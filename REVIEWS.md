# Customer reviews: testing and launch

## Preview workflow

Use a protected Deploy Preview. Open `/review` or `/ar/review` for customer submission and `/admin/reviews` for staff. Leave the production launch flag unset. The API recognizes only Deploy Previews and the published production context; local dev serves the pages but intentionally does not accept reviews through the API.

Open Manage and search for 'Identity'. Ensure registration is invite-only and configure staff invitation and recovery links to open `/admin/reviews` on the protected preview before sending any email. Invite a synthetic test account and give it the server-managed `review-preview-moderator` role only. Never send staff invitation links to a page with analytics. The dashboard does not function while self-signup is enabled. For a real launch use separate, individually invited staff with the `review-moderator` role.

1. Create an invitation for a synthetic completed-job reference. Select an expiration from 1 to 30 days and copy the English or Arabic invitation text. The fragment contains the bearer code and stays out of HTTP requests for the page. If a messaging app strips the fragment, copy the code after `#invite=` into the review form. Forwarding a valid unused invitation can transfer the ability to redeem it; review the job reference before approval. Do not give out invitations based on expected ratings.
2. Submit as the synthetic customer in both languages. Confirm only the pending acknowledgement appears, the code cannot be reused, and the photo is not public. Attempt an expired/revoked link and a bad or oversized image. Use Android and iOS WhatsApp browsers; test the manual code and share fallbacks there.
3. Sign in as the moderator, verify the job, review the photo and text for private details, and approve. Confirm the customer name, text, rating, photo and Kuwait date appear on both homepages. Reject or delete and repeat the public list/photo requests; both must remove the entry immediately for new requests. Try the same administrative API with no account and with a staff account without the preview role.
4. Confirm the preview has a separate database branch and deploy-scoped Blob store. Verify that preview APIs cannot read production-scope records or photos, even with known IDs, and that preview staff have no production role. With synthetic fixtures only, check both directions before accepting any real data. Netlify database branches may inherit production rows. Logical scope filtering prevents the application from serving another scope; it does not prevent physical copies. Before launch, ensure future non-production branches are not seeded with live customer rows or limit future previews to an isolated database. Keep production disabled if that boundary cannot be verified.

## Physical database isolation gate

Netlify Database creates automatic Deploy Preview branches from a snapshot of the production data. Its branch API can choose a parent for an individual named branch, but that does not change the default for future automatic previews. Do not use post-copy deletion, a migration, role checks, or review scopes as evidence that a copy never existed. Do not reset or modify a production database to test this.

Do not use this site's automatically branched database for both real reviews and future previews. A proposed Netlify-native topology is to leave this site's preview database synthetic-only and put live reviews in a separate, approved Netlify Database project that does not create previews of its data. Only the production server runtime would be able to connect to the live database, with no fallback to the website's auto-forked database. This topology is not provisioned. Before using it, rehearse with two isolated non-production projects: put a uniquely marked synthetic review in the production-like store, create a fresh automatic preview, and verify the marker is absent in the new database itself, not just from its API. Confirm the preview has no access to the other database or photo store, and that the separation also holds for subsequent fresh previews. Do not put any real data into either project for this check.

## Hosted Identity and device test handoff

Use a protected preview that already has a safe invite-only Identity configuration, or a separately approved preview-only Identity project. Do not change shared production registration or callback settings to test this. Before sending mail, verify that both email flows land on the protected preview's `/admin/reviews`, not the production site or a page with analytics. Use a synthetic inbox and two individually invited test accounts: one with only `review-preview-moderator` and one without any review moderator role.

- Pass the outer preview gate first. With no Identity session, confirm the app's `GET /api/reviews/admin` returns 401. With the plain staff session, confirm it returns 403. For the preview moderator, confirm login succeeds and the same request returns 200 with the queue. Use `GET /api/reviews/list` and the synthetic approval workflow to validate hosted database reads and writes. Record status codes and outcomes, not cookies, email links, passwords or tokens.
- Pair one Android and one iOS WhatsApp tester with the preview moderator. On each device open the English and Arabic review links inside WhatsApp and test RTL, star selection, manual code entry and pending confirmation. Create a separate single-use invitation for each submission. Test photo visibility while pending, after approval and after deletion with a synthetic image, then remove the test review. Record OS and WhatsApp versions and PASS / FAIL / NOT TESTED for each step. Desktop browser emulation does not count as device evidence.

## Data and retention

- Public responses contain only approved display names, written experiences, stars, dates and authorized photo URLs. The average and count are based on all approved rows; the homepage shows the latest 12. An empty database has no displayed numeric rating.
- The review requires publication consent. It does not collect customer contact fields. Customers can request removal at the site's existing WhatsApp contact. Staff should not include a customer's name, phone number, or address in an internal job reference or audit reason.
- Photos are re-encoded as WebP; originals, GPS/EXIF and filenames are not retained. A staged upload is eligible for cleanup after an hour. Failed uploads and photos removed by moderation are deleted immediately when possible, with retries during later writes and a production cleanup job every six hours. A rejected or removed photo is never returned by the public endpoint, even if storage deletion has to retry.
- A rejected review's public access ends immediately; its name and text are scrubbed after 30 days by cleanup. Delete scrubs its name and text immediately and preserves a minimal status, rating, invitation association and moderation history to prevent reuse and support audit. Pending content stays private until acted on; approved content stays public until rejected/deleted. Invitation hashes, job references, review status tombstones, and moderation events remain for operational audit; review the retention period for these records and platform backups before launch. Fixed-window hashed rate-limit identifiers are removed when older than one hour on cleanup.

## Launch controls

Do not publish this change or enable acceptance of real data without separate approval. Verify hosted preview tests, including migration application, actual Blob IO, Identity access and physical isolation. The approval to launch does not replace the isolation gate: do not set `REVIEW_PRODUCTION_ENABLED` until real reviews are stored outside the database that automatic previews can copy. Configure the production staff role and invite-only workflow. Only after these requirements are verified and the project owner has approved launch may the flag be set to `1` for the production Functions runtime and the approved production deploy be published. With the flag unset, the production feed stays empty and customer submissions, photos, and moderation remain disabled. The canonical origin and domain settings are unchanged.

## Automated verification

- `pnpm typecheck` and `pnpm test` exercise the UI contracts and request security. PostgreSQL tests are opt-in with `RUN_REVIEW_DB_TESTS=1 pnpm exec vitest run src/server/reviewStore.integration.test.ts` against an isolated, non-production PostgreSQL connection with permission to create and drop a temporary schema. Do not run them against production. The integration suite uses synthetic rows and a test-only media double; it does not prove Netlify Blob isolation or Identity behavior.
